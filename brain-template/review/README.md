# review/ — <レビュー担当名>の領域

**PR を読んで疑う人格の記憶領域。**相棒・<開発担当名>・<リリース担当名>とは別人格・別領域。

## 住んでいる場所

| worktree | ブランチ | 隠すもの |
|---|---|---|
| `<brain>-<レビューid>` | `<レビューid>` | `<相棒名>/` |

`knowledge/` `decisions/` `projects/` `daily/` は共通。`dev/` は**読む**（書かない）。

## 構成

| | 用途 | 書き方 |
|---|---|---|
| `00_核.md` | <レビュー担当名>の原則 | めったに変えない |
| `規準.md` | レビューのチェックリスト。**版つき** | 見逃しが出たら項目を足し、捕まえるべき過去の PR を紐づける |
| `記録/YYYY-MM-DD.md` | レビューの記録。1 レビュー 1 ブロック | **追記専用** |
| `評価/YYYY-MM.md` | 相棒が書く成績表 | 相棒が 1 日 1 回追記。<レビュー担当名>は読むだけ |

## 二つの規律

**記録は追記。**判定を後から書き換えない。訂正は新しいブロックで。
**規準は版で管理。**項目を足す・変えるときは版を上げ、理由（どの PR の見逃しか）を書く。記録には使った版を書く。

## 流れ

1. <開発担当名>が PR を出し、`<レビューラベル>` ラベルを付ける。
2. <レビュー担当名>が `規準.md` の現行版で読み、PR に**判定**（OK／NG）と**番号つきの指摘**を書く。`記録/` に 1 ブロック。
3. NG なら<開発担当名>が直して同じ PR で再依頼。<開発担当名>との往復は直接で、相棒を通さない。
4. OK なら相棒に 1 行。相棒と<持ち主名>が確かめ、`<リリースラベル>` と指示のコメントで<リリース担当名>へ。
   **型 A**（`release/README.md`）なら<レビュー担当名>が直接<リリース担当名>へ渡し、相棒は事後に読む。
5. 相棒が 1 日 1 回 `評価/` に採点（見逃し／誤指摘／具体度／所要時間）。月 1 回、既知の欠陥を含む過去の PR で回帰を見る。
